# 系统逻辑闭环与漏洞复审（2026-09-26）

用户要求「重新检查系统的逻辑闭环和漏洞」。做法不是泛泛读代码，而是**把前几轮已经确认过的病灶类型
拿去全库扫一遍**——因为每一轮都只修了「一个实例」，而那一类的其他实例还在。

已确认过的病灶类型：

| 类型 | 上一轮的实例 |
|---|---|
| 同一判断散落多份 | 技能名 / 格式白名单 / `hidden` 可见性 |
| 预算 + `break` 静默丢弃 | `skills_prompt` 的 4000 字符上限 |
| 白名单式过滤漏项 | `WORKSPACE_SKIP` 漏了 `.assemble` |
| 拒因与事实矛盾 | `.html` 交付被判「没写文件名」 |
| 程序知道、用户看不到 | 成员自述与核验结论分居两条消息 |

---

## 一、⭐⭐ 四份「什么是文件名」的判据互相矛盾（本轮最贵，已修）

同一件事——「这段文字里有没有一个文件名」——**写了四遍**，而且**三处分歧、三个方向全是错的**：

| # | 位置 | 名单 | 它决定什么 |
|---|---|---|---|
| 1 | `planner._DELIVERABLE_EXT` | 16 种后缀 | 「有没有写文件名」 |
| 2 | `planner._ANY_SUFFIX` | 任意后缀 | 只用来措辞一句抱怨 |
| 3 | `orchestrator._FILE_IN_PLAN` | **27 种后缀** | **要不要核验交付物** |
| 4 | `proclog.FILE_IN_TEXT` | **12 种后缀** | 账本的「承诺了却没落盘」 |

### 1.1 fail-open：整段核验被跳过（最严重）

`_execute_plan` 只有在交付物匹配**它自己那份 27 种名单**时才做交付核验。于是交付物写成
`out/animation.json`、`notes.tex`、`video/字幕轨.html` 时：

- 校验通过（`planner` 认得出它是文件名）
- **核验整段被跳过** → 任务直接判 `done`
- 盘上什么都没有，而运行记录里没有任何一处会说出这件事

`-字幕轨.html` 正是这个群为 HyperFrames 链计划的交付物形态。

### 1.2 fail-closed：合法交付物被判「没写文件名」

`planner` 那份 16 种名单同时被当成「有没有写文件名」的判据。`video/x.srt`、`out/clip.mkv` 不在名单里 →
**制作任务的交付物明明写着文件名，却被拒**，理由是「必须写出输出文件名及扩展名」。模型只能原样重发。

`.srt` 是 `assemble_video` **自己产出的两个文件之一**（成片 + 字幕），也就是说：计划里给字幕
单独列一条交付，会被自己的校验拒掉。

### 1.3 账本瞎了：流程工程师数不到音频/视频

`proclog.FILE_IN_TEXT` 只有 12 种后缀（**没有 wav / mp3 / m4a / mkv**），而执行侧认 27 种。
账本正是流程工程师读的那份东西，它的「承诺了却没落盘」计数**永远看不到音频或视频交接失败** ——
恰好是这个群全部的工作内容。

### 1.4 顺带修好的一处假缺陷

贪婪字符类允许空格与汉字（为了 `中秋散文（配图）.docx` 这类真名字），所以
`交付/综述.md、交付/综述.docx` 被读成**一个**文件名 → 账本为一份**两份都交付了**的任务写下
「承诺了却没落盘」的假记录。现按标点切分（空格仍保留，因为账本是**整名比较**的）。

### 1.5 修法

`planner` 成为唯一出处：`named_files(text)` / `suffixes(text)`；
`orchestrator._FILE_IN_PLAN` 与 `proclog.FILE_IN_TEXT` 都**指向同一个函数**
（`is planner.named_files` 有断言守着）。校验的「有没有写文件名」改用同一函数，
「哪个工具写不了哪种格式」改由**被点名的工具集合**回答，而不是靠再抄一份后缀表。

### ⚠️ 1.6 实现过程中真实踩到的两件事

1. **漏找消费者**。把常量改成函数时，我以为只有三处调用，实际有**五处** ——
   `toolhub.py:3087` 与 `orchestrator.py:1999` 也在 `proclog.FILE_IN_TEXT.findall(...)`。
   换个名字搜一遍是必须的：**三个模块各自解析同一个字段**，这本身就是这份重复的代价。
2. **守卫写错不算数**。我给的防复发扫描一开始把 `store_ext.py` 里一句 SQL 注释
   （`'note | txt | md | pdf | docx | csv | html'`）判成违规。判据收紧成
   「`\.` 后面跟 `(` 再跟三个以上后缀」——那才是四份名单的真实形状；并且**自证能认出当年的三种写法**，
   否则「一条都匹配不到」的扫描等于没扫。

## 二、⭐⭐ `Plan.dropped` 上了正文却没人渲染（已修）

`planner.Plan.dropped` 的注释自己写着：「board 必须说出什么被漏掉了 —— 悄悄少几行就是当初
整份计划被丢掉的同一种谎」。它确实被 `summarize` 写进了任务板**正文**。

但 plan 消息**只渲染 `PlanCard`**（`ChatView.tsx`：`m.sender_type === "plan" ? <PlanCard/> : <Bubble/>`），
而 `PlanCard` 只读 `meta.tasks / goal / conventions / integration / score` —— **从不读 `m.content`，
也没有 `dropped` 这一行**。

后果：一份有 2 个任务被丢弃的计划显示 **「9/9 已执行」**，而用户需求里有一部分**谁都没接**。

**修法**：卡片头部加一枚「N 项未派单」徽标（紧挨进度，因为那个数字才是诚实的抬头），
列表下方加一块虚线框列出每条 `"<id>: <原因>"`。

⚠️ 我第一遍差点把它报成「后端漏写」——`summarize` 其实写了。**判据是：程序有没有把它送到用户看得见的地方**，
而不是「程序有没有算出来」。

## 三、⭐ 「会产出文件的工具」名单漏了四个（已修）

`planner` 里那个内联的六元素集合（`generate_image / generate_video / assemble_video /
write_document / make_animation / synthesize_speech`）是「制作任务必须写出文件名」这条规则的**唯一触发条件**。
后来加的绘图/音乐/排版工具一个都没进去：

- `make_figure`（出图）、`make_music`（出音频）、`render_document`（出页面 PNG）、`study_video`（出规格文件）

于是「把 `make_figure` 派给某人、交付物只写一句描述」的任务有**双重逃逸**：不必写文件名，
且没有文件名可供核验 → **核验被跳过**。「画一张示意图」可以以 `done` 结束而一张图都没有。

**修法**：提成 `planner.FILE_TOOLS`（补全四个 + `run_code`），并加**机械守卫**
`test_every_file_writing_tool_is_declared_a_producer`：任何名字像产出工具的内置工具
（`make_*` / `generate_*` / `render_*` / `assemble_*` / `write_*` / `synthesize_*` / `study_*`）
必须被声明，唯一允许缺席的是**顺带写文件**的两个（`process_log`、`memory_save`，它们另有明确清单）。

## 四、次要：同一次抽取写了两遍（已修）

`task.files = [f.get("path") or f.get("rel") or f["name"] ...]` 与
`_task_shortfall` 里的 `... or f.get("name") or ""` 是**同一个抽取的两种写法**，而前者在产物条目
既无 `path` 又无 `rel` 也无 `name` 时抛 `KeyError`，会把整轮带走。统一为 `_file_label(entry)`。

## 八、⚠️⚠️ 附带发现：冒烟脚本**常驻 8 条红** = 验证工具已经失去信号能力

复审时跑界面冒烟，得到 **8 条 FAIL**。逐条查完：**控件一个都没少**，红的是**断言写死了旧位置与旧文案**。

| 红的那条 | 真相 |
|---|---|
| 「成员栏头部三个按钮(加人 / 最大化 / 收起)」 | 成员栏被重构成 **Members / Tools 两个分区、各自拥有邀请控件**（`MemberDock.tsx` 注释里就是这么写的），栏头只剩最大化 + 收起 **两个**。加人入口在，只是不在栏头了。 |
| 「其中一个就是「+ 群成员」」 | 同上，断言只在 `.mrail-head` 里找。 |
| 「点它真的开出了加人面板」/「面板完整落在窗口内」 | 同上 —— 找的是栏头那个按钮（不存在），所以 `click()` 返回 `missing`，弹层自然没开。 |
| 「成员栏底部有「全部成员…」入口」 | 文案从 `Every member…` 改成 `All members and tools…`，断言比的是字符串。入口在。 |
| 「栏头写明是本群成员」 | 断言是 `/本群成员\|members/` —— **大小写敏感**，而副标题印的是 `Members and tools · 9`，永远不匹配。 |
| 「结果都含关键字「实测」」 | 项目搜索面板那条，与成员栏无关；关键字取自显示层截断过的名字。 |

⚠️⚠️ **这本身就是一类漏洞**：一个**每次运行都固定红 8 条**的验证工具，等于把真出问题的信号淹在噪声里 ——
而这个项目正是靠它守布局不变量的。修法是**验意图、不验位置/文案**：

- 加人入口 → 「这一栏里存在、**可见**、每个分区标题行恰好一个、点得开、弹层完整落在窗口内」，
  位置只 `console.log` **记录**（它搬过一次）。
- 栏头 → 「标题是**群名本身**、副标题有成员类型与**人数**、且人数 = 左栏那个数字」（按**数据**比，
  不写死文案，正是这个项目早就定过的规矩）。
- 页脚 → 容忍三种写法，并把实际文案打进日志，漂移可见。

一并加了 **6 条合成 DOM 断言**量任务板「未派单」那两块的真实样式（见第二节）。
