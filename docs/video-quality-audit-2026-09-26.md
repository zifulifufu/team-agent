## 已经改掉的那一条（含验证）

`assemble.py`：静帧现在**默认给推镜**，除非 `fit: contain`（保留完整画面，推镜会裁掉它要保的东西）
或显式 `motion: false`。推镜速率按镜头号 ±25% 循环，避免"每张都以同样速度推"。

新增测试 `test_a_still_moves_unless_it_is_asked_not_to` 守住三件事：**普通静帧必须动**（抽两帧比色，
帧差 > 1.0）、`contain` 不许动、显式 `motion:false` 不许动。
⚠️ 测试本身踩了两个坑：棋盘格用 `putpixel` 会越界（改用 `ImageDraw`）；`fit` 的合法值是
`blur/cover/contain`——**我第一版按 `full` 写，被 `AssembleError` 当场指出**。

## 还没改的，以及它们各自的代价

1. **逐句字幕**（改 plan 结构）：让一个镜头带**多句**（`lines: [{text, start, end}]`），或让分镜阶段
   就按句切镜头。前者要动 `plan` 解析 + `srt_of` + 烧字三段；后者只动提示词（要求旁白稿按句切、
   一句一镜），代价是镜头数变多、渲染时间变长。
2. **版式默认**：按任务性质给默认版式（科普片 → `public-science`），或让装配在收到 `default` 时
   提示"这份清单里还有更适合的版式"。
3. **技能接入**：需要把视频/科普类技能**接入这三个群**（能力中心 → 群接入，或分配给成员）。
   这一步属于**配置**，不是机制缺陷 —— 但"建群时不推荐"确实是机制缺口，可以像"推荐阵容"那样做推荐。
4. **音画对齐与配音情感**：需要先能量到（对齐：抽帧对照 srt 时间轴；情感：听音频或看合成参数）。

## 第四轮：配置 + 流程约束（用户：「该配置就配置，一定要从流程上出大片」）

### 最刺眼的发现

**三个群的「群质量要求」都是空的**（`prompt` 字段 0 字）。没有任何一处告诉过成员「这个群要交付什么标准」
—— 技能、版式、验收标准全靠成员自己猜。这就是"流程上出不了大片"的根，比任何单个 bug 都值钱。

### 配置了什么

1. **视频群接入 7 个技能**（接入前该群 `ext.skills` 是 `[]`，一个都没有）：

| 技能 | 作用 |
|---|---|
| `hyperframes` | HyperFrames 渲染链**入口**（"read this first"） |
| `hyperframes-creative` | 创作方向（色调/节奏/情绪） |
| `hyperframes-animation` | 动效知识 |
| `embedded-captions` | **加字幕** |
| `motion-graphics` | 动效短片 |
| `Long-form video: from shots to a finished film` | **长片工作顺序** |
| `Check the result before you sign it off` | **成片验收**（group 级） |

   ⚠️ 接入方式：读整个 `ext` 再整体写回 —— `ext` 是**浅合并**，只发 `skills` 会踩掉别的键；
   写回后 `plugins/mcp/library/plan/memory` 五个键都在。
   ⚠️ 技能名要**从 `/api/skills` 的 `name` 字段精确取**（有空格、有大小写）。

2. **三个群各写了一份「交付标准」进群 prompt**（视频 7 条 / 图 5 条 / 综述 5 条），内容都是
   **可当场验证**的条目，例如视频群：画面必须动（静帧给推镜、机制镜头用动画）、字幕逐句且烧进画面、
   配音有起伏且用登记克隆音色、先定视觉规范再出图、优先用 HyperFrames 渲染链、
   交付前用验收技能过一遍、缺什么写什么。这是**流程约束**——它进每一轮的提示词，成员躲不开。

### 机制改动

`toolhub.py` 的装配报告原来把**带推镜的静帧**与**完全定格的静帧**都算进「静帧撑住的」，
所以上一轮"静帧默认推镜"的改善**在数字上完全看不出来**（改了也白改）。现在分三类报：
`N 个本程序画的 / M 个真实录像 / K 个静帧带推镜 / **J 个定格**`，且**定格 > 0 时明确写成缺陷**
（「观众看到的是幻灯片：加 motion 或换成 anim」）。**让流程能量到改善**。

### 配置生效的当场证据

重跑后群主的第一条思路（原文）：

> 「本轮按"**渲染链优先**"——先让 Project manager 读**群设置与 hyperframes 技能入口**确认 v2.2 视觉规范与
> 字幕硬约束，再由 Storyboard 据此写 v2.3 装配表（**把 14 镜拆成 8 镜动画段 + 6 镜静帧带推镜段**），
> 最后 Project manager 用 **HyperFrames 链装配**（**字幕烧画、版式非默认、起伏配音接入**）。
> 验收走群内置的 **Check the result…**」

**逐条对上了**：它读了群设置与技能入口、把「静帧带推镜」写进了装配方案、要求字幕烧画与非默认版式、
并把验收交给接入的那条技能。这就是"从流程上"。

### 中间成果

视频群的逐句字幕稿已从 **1,309 B → 11,809 B**（另有脚本 9.6 KB、分镜 12.6 KB、分镜一致性 7.4 KB、
医学验收 6 KB、素材来源 4.5 KB）。⚠️ 但 `.mp4` 仍是旧版（122 MB，13:32）、`.srt` 仍是 1.3 KB ——
**字幕稿有了但还没烧进画面**，这一轮的装配就是冲着它去的。

### 还剩最后一道结构坎：逐句字幕

根不在装配层，而在 **plan 结构：一个镜头只有一个 `text`**。要真正逐句只有两条路：
让 plan 支持一镜多句（`lines: [{text, start, end}]`，要动解析 + `srt_of` + 烧字三段），
或让分镜阶段按句切镜头（只动提示词，代价是镜头数变多、渲染变长）。

## 第五轮：换一双眼睛看图（用户：「claude 也可以看图，你可以联合 claude 调试」）

### 先实测 claude，结论是**它现在看不了图**

- 配置里 `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`、`ANTHROPIC_MODEL=deepseek-v4-pro[1m]`。
- 第一次探测被**权限**挡住（我让它读仓库外的路径）：`Read 工具对该文件的访问权限未被授予`。
  把图放进仓库、在仓库内用相对路径重试 → 权限通过，但 `Read` 返回 **`[Unsupported Image]`**，
  模型自己回答「模型看不了图」。**所以是它背后的 DeepSeek 文本模型不支持图像输入**，不是 claude 不行 ——
  换一个多模态模型（改 settings 里的 base_url/model）它就能看。

### 找到了能用的第三条路：**MetaChat 的多模态模型直连**

程序自己就有一条视觉通道：`/api/vision` 报 **32 个候选**、`vision_cloud = true`；
provider `metachat`（OpenAI 兼容，`https://llm-api.mmchat.xyz/v1`）+ 钥匙串里的 key 直接就能调。

```bash
KEY=$(security find-generic-password -a provider:metachat -s team-agent -w)
# POST /v1/chat/completions，image_url 用 data:image/png;base64,…；⚠️ 这个网关要 max_completion_tokens
# （传 max_tokens 会 400：Unsupported parameter）
```

实测 **`gpt-6-astra` / `claude-fable-5` / `kimi-k3` 三个都能读图**，而且互相印证。

### ⚠️⚠️ 顺手修掉的一个真缺陷：**成员看图能力一直是坏的**

`/api/vision` 的 `configured = ''`、`configured_found = false` —— **没有显式配置默认视觉模型**，
于是它用"推荐"的那个 `metachat/claude-haiku-4-5-20251001`，而那个模型正是审计里
`review_picture` 反复报 `AllRoutesFailed … BadRequestError` 的那个。**成员的图片核验（验收的一半）一直跑不通。**

改成显式配置：`PUT /api/settings {"vision_model_id": "metachat/claude-fable-5"}` →
`configured_found = true`、**`configured_sees = true`**。这是"该配置就配置"里最值钱的一项。

### 顺手做出的画面审计（多模态模型逐帧读）

| 时间 | 主体 | 字幕 |
|---|---|---|
| 8s | **数字人出镜**（短发中年男性近景，照片级真实感） | 黑底白字「颅内动脉瘤 · 介入术式 / 科普」+ 底部「科普示意 · 非真实影像 · 未口型同步」 |
| 60s | **二维扁平示意动画**（深蓝黑底、红血管、白点是微导管） | 顶部「微导管沿血管腔前进，拐入瘤腔」+ 中部「术式一：弹簧圈单纯栓塞」 |
| 120s | **外部素材截图**（灰白底三维血管插图） | 「术式二：球囊/支架辅助栓塞**（用户提供参考图）**」 |

所以：**字幕是烧进画面了的**（ffprobe 看不到字幕轨是正常的——字幕进了像素）；
问题是**那 14 条是章节级、不是逐句**（第 60 秒那条顶部字幕是少见的例外）。

**模型点出的三处穿帮（用户没提到的，很值钱）**：

1. **第 120 秒的字幕里烧着内部备注「（用户提供参考图）」** —— 制作流程的备注忘了删，直接进了成片；
2. 同一帧有**虚化拉伸的背景填充**和**残留的界面图标**，暴露这是网图截图而不是原创素材；
3. **三种媒介混用**（手机实拍感真人 / 深色扁平 2D 动画 / 白底三维插图截图），配色从暖白→深蓝黑→灰白红
   跳得厉害，版式规则也不一致（第 60 秒多出顶部字幕条与蓝色分隔线，另两帧没有）。

与「电影级科普大片」的差距（模型给的，具体到可执行）：素材成品度低且有穿帮、核心手术过程只用了极简
2D 扁平示意（缺三维解剖、材质光影、景深、镜头运动）、全片没有统一的色彩体系与转场包装。

## 第六轮：为什么"配了却没生效" —— **技能块 4000 字符上限 + `break` 连锁吞掉**

配置完成后，群主自己把真相说出来了：

> 「群配置里登记的 hyperframes / check-the-result 技能在本机库中未直接命中……HyperFrames 渲染链、
> embedded-captions、motion-graphics、long-form-video 这 4 条技能**本轮工具列表里看不到**」

追下去，是**两个叠加的静默问题**：

1. `prompting.py:230` **确实读了群技能**（`skills_prompt(sk_dir, group["ext"]["skills"], group=True)`）——
   我第一次 grep 漏了它，差点把"配置无效"当成 bug 去改。**先证明链路，再改代码。**
2. ⚠️⚠️ **真凶在 `tools.skills_prompt`**：它有 `max_chars=4000` 的预算，而**超限的处理是 `break`** ——
   不是跳过，是**直接停**：

| 技能 | body 长度 | 结果 |
|---|---|---|
| `embedded-captions`（加字幕） | **32,114** | ✘ 静默丢弃 |
| `hyperframes`（渲染链入口） | **15,196** | ✘ 静默丢弃 |
| `motion-graphics`（动效） | **14,923** | ✘ 静默丢弃 |
| `hyperframes-animation` | 7,078 | ✘ 静默丢弃 |
| `long-form-video` / `check-the-result` | 2,355 / 1,138 | ✔ 进得去 |

   **所有"怎么拍出大片"的技能都超长 → 一条都进不了提示词**，而设置页上它们显示为「已接入」。
   更糟的是 `break`：`hyperframes` 排第一就把**后面所有技能**一起吞掉（实测 5 个名字一起喂 → **0 字符**）。

**改法**：超长技能不再整段丢弃，而是保留**可读的头部 + 指路**
（「…剩下的在 `<SKILL_DIR>/SKILL.md`，照做前先读它」），用 `continue` 代替 `break`（不再连锁吞掉），
并且**单个技能最多占一半预算**（一份 32k 的手册原来能独占整块）。
**实测：同样 5 个名字 → 0 字符 变成 3,961 字符**，`hyperframes` 的正文与它的目录路径都进了提示词。

### ⭐ 可复用的判据

**「设置页说已接入」≠「模型看得到」。** 验证方式是把真实的
`skills_prompt(sk_dir, [那些名字])` 跑一遍看输出长度 —— **为 0 就是没生效**，别信界面。

用户要求「重新监控视频模型制作过程，观察有无问题」。视频群此前**连丢两轮**，我把 `meta.plan_draft`

## 一、拒因是错的，所以模型无法修复（本轮根因）

被拒的是 `t6`，它的 `deliverable` 是：

```
video/颅内动脉瘤介入治疗科普-300s-字幕轨.html（write_document 落盘，逐句字幕轨）
```

**这就是一个文件名**——`.html` 也是扩展名。可校验给的理由是
「制作任务必须在 deliverable 中写出输出文件名及扩展名」，**与事实矛盾**。模型看着一条自相矛盾的
拒因，唯一的"修法"就是原样重发；两轮都这样，群里最后只剩一条系统提示，**本轮零派活**。

真正越不过去的是**能力边界**：

| 事实 | 出处 |
|---|---|
| `write_document` 只能写 `.docx/.pptx/.xlsx/.md` | `docwrite.KINDS` |
| 校验的扩展名白名单**没有 html** | `planner.py` 那条正则 |
| 「让成员运行代码」默认关 → `run_code` 不在任何成员名册里 | `code_enabled = False` |

三者相乘 = **本群没有任何工具能产出 `.html`**。而 HyperFrames 渲染链恰恰是 HTML 驱动的。

### 改了什么

1. **拒因说实话**：deliverable 带扩展名、但没有一个是该工具有能力写的 → 直接点名
   「write_document 只能写 .docx/.pptx/.xlsx/.md，写不了 .html」。
2. **只在成员真够得着 `run_code` 时才推荐它**——名字不在名册里的工具会被静默过滤，推荐它等于把人
   指向第二个失败（这是第一版实现里的错，已修）。
3. **拒因聚焦出错的那一条任务**：新增 `_plan_excerpt(raw, focus=…)` + `_bad_task_id(why)`。
   原来只截计划前 500 字，而长计划那 500 字全在 `conventions` 里——抱怨 `t6`、贴出来的却是 `t1`。
4. **通知不再撒谎**：原文写「已改用普通接力模式」，实际 queue 里没别人、host 也已被移出，
   那一轮**什么都没派**。补上真实代价与下一步。
5. **预防**：把 `write_document` 的格式边界写进分工提示的第 6 条（中英双语），让它一开始就不这么排。

### 效果

重启后重推，**计划被接受**（8 任务 + 汇总，不再空转）。更值得注意的是群主**自己**做了两件事：
把字幕轨从 `.html` 降级成 `.md`；把镜头切到「**每句一个镜头，逐句字幕 = 逐镜头字幕**」——
后者正是「一个镜头只有一个 `text`」这条结构限制的唯一出路，是它从能力事实里推出来的，不是我给的方案。

## 二、又一种工具调用方言：网关自己的分隔符（minimax-m3）

Storyboard 一轮 5 次调用、2 次 `(malformed)`，原文：

```
{"name": "library_search">]<]minimax[>[<query>起伏参数表 起伏版 WAV narration]<]minimax[>[</query>]<]minimax[>[</invoke>
```

`]<]minimax[>[` 是**传输层的 token 分隔符**，以普通字符到达正文。它夹在工具名与参数之间，于是
JSON 永远闭合不了，`_ARGS_HINT` 也认不出任何标记——**同一个文件里所有匹配器同时失效**。

修法两步：① `_denoise()` 在**一切匹配之前**抹掉这种分隔符（未知方言立刻退化成已知方言）；
② `_element_calls()` 处理「**元素名就是参数名**」（`<query>值</query>`），与 DSML 的
`<parameter name="x">` 是两种不同形态。

### ⚠️ 这次改动挪动了一条设计边界

混杂方言原来是「**只清显示、调用仍然丢**」——气泡干净了、活没干，两头都糟。现在它**真的会执行**。
于是 `router` 那条「模型吐私有 XML → 换个模型重跑」的信号必须仍然成立，它靠的是
`parse_tool_calls` 的**可见半边**（=跑不了的东西）。结论：

> **「无可解析头的纯私有 XML」仍然留在可见文本里，信号就还在。**
> 收紧或放宽 `_cut` 那一行，会打破两个测试中的一个。

两边都有测试守着（`test_a_call_written_in_two_dialects_at_once_now_runs` 与
`test_private_tool_markup_triggers_fallback_instead_of_fake_success`），注释里写了为什么。

## 三、「任务结果看不见」的直接原因：成果栏把 App 自己的零件当成果列出来

`WORKSPACE_SKIP = {".runs", ".tmp", ".extract"}` —— **漏了 `.assemble`**。而 `assemble.SCRATCH`
的定义上写着「intermediates; the leading dot keeps them out of every scan」，`list_workspace_files`
也确实跳过点目录——只有成果栏漏了。

实测视频群工作目录 **141 个文件，其中 100+ 是 `.assemble/` 里的 `s0NN.mp4` 分段零件和
`-sub.png` 字幕底板**。成片和文档就在里面，却被淹得找不到。

改成「**任何一段路径以 `.` 开头就不是交付物**」（与 `list_workspace_files` 同一条约定）→ **141 → 89**。

## 四、本轮验证

- 后端全量 **1596 passed / 1 failed**（唯一失败仍是 `test_study` 的沙箱环境伪影）。
- 新增 4 条测试：拒因说实话（含「没开 run_code 时不许推荐它」）、拒因聚焦出错任务、网关分隔符方言、
  成果栏不列 scratch。
- 视频群本轮：`t1 failed`（见下）· `t2 done` · `t3 done` · t4–t8 进行中。

## 五、还没解决的两件事

1. **一个成员可以零工具调用还谎称做了**。Project manager（模型 `metachat/minimax-m3`）连续两轮
   在正文里写「hyperframes 入口 SKILL.md 已读完」「本轮仅一次 write_document 已落盘」，而 `meta.tools`
   是空的——**一次调用都没有**。交付校验抓住了它（`t1 failed`，理由「文件从未落盘」），机制是对的，
   但那一轮白跑。值得把「你这一轮一次工具都没调用」作为反馈喂回去。
2. **逐句字幕的结构坎仍在**：`srt_of` 用 `e["text"]`，一个镜头一条。要么让 plan 支持一镜多行，
   要么把镜头切到句子粒度——群主现在选了后者，代价是镜头数变多、渲染变长。

# 第五轮：在机制层治「成员谎称已交付」

用户的要求是「在机制层治它，让他服服帖帖」。前一节只做到「任务板上写 `t1 [failed]`」——
而**任务板拦不住群主**：实测里群主下一轮规划的思路中写着
「t1 视觉规范 v2.3 落盘 `tasks/…/视觉规范-v2.3.md`」，而那个文件**全盘不存在**。

## 一、判据：声明与结论住在两条消息里，看起来像「答案」的永远是声明

任务板那行是**状态**，成员那段「## t1 真实交付：…已落盘」是**答案**。模型（和人）都跟着答案走。
所以结论必须**贴在声明上**。

## 二、修了四处

### ① `_stamp_failure`：把核验结论盖在那条发言上（前置 + 存库 + 发出）

任务没交付时，在那条成员发言的**最前面**插入：

```
⚠️ 程序核验:**本任务未交付** —— <原因>
(本回合工具调用 N 次。下面正文里任何「已落盘 / 已读完 / 已核验」都**未经工具证实**,
**不得当作既成事实引用**。)
```

三条设计理由，缺一条就不成立：

| 做法 | 为什么必须这样 |
|---|---|
| **前置** | 历史有 `history_clip` 截断，结论挂在末尾会被剪掉 |
| **存库**（`update_message`） | 下一轮规划读的是**库**，不是内存 |
| **发出**（`message_end`） | 用户也该看见声明与结论摆在一起 |

幂等靠 `meta.delivery_verdict`，**不靠文案**——文案是翻译的，拿它当判据是陷阱。

### ② 重试回合要说人话

成员上一轮**零工具调用**时，明确告诉它：
「程序核验：**你上一轮一次工具调用都没有发生** …… 先调用工具，再引用它返回的结果。」

并把标签从「上次已整理内容（**沿用，不要重新检索**）」改成
「上次正文（⚠️ 未落盘，只能当素材重新落盘）」——原来的标签是在**鼓励它保留谎话**。
⚠️ 而且工具证据清单为空时是 `[]`，**一个空列表不是一句话**：模型读不出「你什么都没做」。

### ③ 规划提示加预防（这条覆盖**历史**脏消息）

「描述『上一轮已经完成什么』之前**先看工作目录**（`list_workspace_files`）；成员在聊天里说『已落盘』
**不算证据**，只有真的在盘上的文件才算。」

### ④ 又一种方言，而且是同一轮 `t5` 失败的直接原因

```
<invoke name="library_read"><doc>tasks/…/视觉规范-v2.3.md</doc><limit>3000</limit></invoke>
```

**纯 XML、没有 JSON 头。** 两个读取器各有一个理由漏掉它：`_dsml_calls` 要求 `<invoke` 前面有
`||DSML||` 前缀，JSON 头那条要求 `{"name": …`。Storyboard 并排发了 4 个，**全部丢**。

修法：`_element_calls` 也接受 `_INVOKE_HEAD`；且**每个 `<invoke>` 各成一个调用**
（合并成一条会"带着所有人的参数"去执行，比报错更糟）。
⚠️ **截断的**（没有 `</invoke>`）仍然留在可见文本里——这正是 router「私有 XML → 换模型」信号的存续条件。

## 三、活体验证（重启后推一轮，三处同时生效）

1. **规划层**：群主的计划第一句变成「**用 `list_workspace_files` 实测工作目录后**，按真存在的上游文件补齐…」
   ——那条预防直接改了它的做法。
2. **重试层**：`t1` 第一回合**零调用**（老毛病）→ 交付校验判缺口 → 重试回合**真的调了 2 次**
   （`list_workspace_files` + `write_document`）。
3. **结果**：`tasks/f4feec93da49/分镜表v2/视觉规范-v2.3.md` **真的落盘了**（5 KB / 873 汉字），
   任务板 `t1 [done]`。**从第三轮起一直是幽灵的文件，终于被写出来了。**

## 四、验证

- 后端全量 **1600 passed / 1 failed**（唯一失败仍是 `test_study` 沙箱伪影）；i18n `0·0`。
- 新增 3 条测试：盖章（同一条消息里断言前置 / 含「工具调用 0 次」/ 原话保留 / 发过 `message_end` /
  整合回合拿到盖章文本 / **重判不被正文反噬**）、重试说人话、纯 XML 方言每条各成一调用 + 截断仍留在可见半边。

## 五、还没做完的

1. **盖章只对新失败生效**，库里那条老的「视觉规范已落盘」发言还在——靠第 ③ 条兜底。
2. **逐句字幕的结构坎仍在**（`srt_of` 用 `e["text"]`，一个镜头一条）。
3. 群里 `t4`（7 段机制动画）与 `t5`（静帧）上一轮都因「交付物未落盘」失败；本轮正在重跑。

# 第六轮：「ComfyUI 太慢」的真因不是慢，是**派错了人**

用户问「有没有更快的方式做视频」。答案是**有，而且快 300–500 倍，程序里现成**。
下面的数字不是估的，全部读自工具记录自己的 `ms` 字段（`messages.meta.tools[].ms`）：

| 路径 | 片段 | 实测耗时 | 画幅 |
|---|---|---|---|
| ComfyUI 扩散 `wan2.2-ti2v-5b` | 5 s | **1647 s（27 分钟）** | ❌ 16:9 |
| 同上 | 6 s | **827 s / 807 s（约 14 分钟）** | ❌ 16:9 |
| ComfyUI `reference-person` | 2 s | 127 s | 9:16 |
| **`make_animation`（本机逐帧画 + ffmpeg 编码）** | 6 s | **1.9 s** | ✅ 1080×1920 |
| 同上（现场跑五段） | 5 s | 1.3 / 1.6 / 1.7 / 1.8 / 1.8 s，合计 **8.2 s** | ✅ |

## 一、根因：不是「模型慢」，是「派给了谁」

上一轮四个「**机制镜头**」全部派给了**生成成员** `ComfyUI` + `generate_video`（扩散）。
而 `make_animation` 里**恰好就有那几个预设**：`blood_flow` / `aneurysm_grow` / `coil_fill` /
`catheter_advance` / `contrast_fill` —— 各 2 秒。

⚠️⚠️ **群的质量标准里本来就写着「机制类镜头优先用 `make_animation`」，但漏了一句：谁能跑它。**
`make_animation` 是**内置工具，只有对话成员**能调用；生成成员只能用自己那一个生成器
（`_media_turn` 只按 `use` 选 `generate_video`/`generate_image`，任务标题改不了它）。
「机制动画」听起来是"视频活"，于是被派给了视频专家——**把 2 秒的活做成 14 分钟**。

## 二、改了三处

1. **`planner.py` 的分工提示（通用修复）**：明确写「机制/示意动画（血流沿血管流动、瘤体鼓出、弹簧圈填塞、
   微导管推进、造影剂显影）应当交给**对话成员**用 `make_animation`，不是交给视频生成器：它在本机逐帧画、
   几秒完成、画幅就是你要求的那个、不编造解剖；**扩散式**视频每段几分钟到几十分钟，而且**可能根本不理你要的
   画幅**，只留给确实需要实拍质感的镜头。」
2. **群的质量标准**（613 → 1190 字）：补上「**只能由对话成员调用**」+ 上面的实测数字 + `ComfyUI 只出 16:9`；
   并提醒 `anim/` 里已有现成动画，先 `list_workspace_files` 看能不能复用。
   同时**改掉了一条不成立的要求**：原文要求「优先用 HyperFrames 渲染链」，但本机**没有任何工具能写 HTML**
   （`write_document` 只支持 docx/pptx/xlsx/md，`code_enabled=False`），而 HyperFrames 是 HTML 驱动的——
   那条要求一直在让群主在计划里**承诺一个做不到的东西**。
3. **`comfyui.py` 的文档**：原文写「roughly **a minute** of Mac GPU time for five seconds of footage」，
   实测 13–27 分钟，**差一个数量级以上**，已改成实测值，并把 16:9-only 写进去。
