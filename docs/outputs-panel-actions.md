# 成果栏：自动展开 + 右键动作（2026-09-26）

用户的两句话：

> 一旦有成果输出自动显示右侧栏，成果可以右击被对应的工具打开或者分享给微信等

---

## 一、有成果就自动展开右栏

`App.tsx` 里新增一个**只在面板关着时**才跑的看门人：每 6 秒读一次这个群的工作目录，
**条数比上一次多**就把面板打开，并提示「这个项目新产出了 N 个文件」。

三条判据，少一条这个功能就会变成干扰：

| 判据 | 不这么做会怎样 |
|---|---|
| **只在条数真的增加时开**（不是「有文件就开」） | 每换一个群、每收到一条没有产出的消息都弹一次 —— 那就成了「关不掉」 |
| **只有面板关着时才轮询** | 面板开着时它自己按群消息时间戳刷新（`OutputsPanel` 顶部那段注释说的「不要一直敲门」正是这个意思） |
| **窗口不可见时不敲**（`document.hidden`） | 最小化时白敲；而可见时那一次 tick 照样会把该开的面板开出来 —— 基线留在 ref 里，不会因为跳过而丢掉「多了文件」这件事 |

⚠️ **两处读数必须互相喂**：面板回填的那个数（`onCount`）也记进这份基线（`takeCount`）。
否则「关一次再开」会把基线丢掉，下一次刷新就被误判成「多了文件」，面板又自己弹开。

## 二、右键一条成果

菜单里五件事 + 分享目标，**按能力渲染**：做不到的项根本不出现（不是灰着、也不是点了没反应）。

| 菜单项 | 它做什么 | 做不到时 |
|---|---|---|
| 在这一栏里看它 | 和左键一样：图片/视频/音频/文档就在旁边看 | 永远在 |
| 用它的默认程序打开 | `shell.openPath(file)` —— 系统给这类文件的默认程序 | 浏览器里不显示 |
| 在访达里找到它 | `shell.showItemInFolder(file)` —— **唯一对所有类型都成立的动作**（100 MB 的 mp4 没有剪贴板装得下） | 同上 |
| 复制这个文件 | 图片进图片剪贴板（可直接粘进微信），其它进路径文本 | 同上 |
| 复制它的路径 | 路径文本 | 同上 |
| 用「微信」打开 … | `open -a <app> <file>`，每个**这台机器真装了**的应用一条 | 没装的不出现 |

**措辞是「用 X 打开」而不是「发送到 X」**：这里做的是 `open -a <app> <file>`，和访达的
「打开方式」完全一样；之后那个程序拿文件做什么（邮件写成附件、微信弹发送面板）是**它自己的行为**，
不是这里能承诺的。要保证能进微信的那条路是「复制这个文件」→ 粘进微信（图片）。

**分享目标是扫出来的，不是写死的**（`team-agent:share-targets` 在 `/Applications` 与
`/System/Applications` 里找一个名单）。这台机器实测扫到 5 个：
`WeChat` / `WhatsApp` / `Mail` / `Messages` / `Notes`（Telegram、飞书、钉钉、QQ 没装 → 不出现）。

**每个动作都回话**（`ui.tsx` 新增 `notify()`，`Toaster` 订阅）。复制这一路尤其重要：
它不是图片时复制的是**路径**，界面必须说清是哪一个 —— 否则用户粘到微信里发现是一行路径，
而界面上写着「已复制」。

## 三、新增的外壳通道（`desktop/electron/`）

`open-path`（原有的）**只接受目录**，成果栏交出的是文件，所以新增：

| 通道 | 判据 |
|---|---|
| `open-file` | 绝对路径 + **真的是文件**（目录、相对路径、不存在、空串一律拒） |
| `reveal` | 同上，`showItemInFolder` |
| `copy-file` | 同上；图片 → 图片剪贴板，其它 → 路径文本；**回报是哪一种** |
| `copy-text` | 非空字符串 |
| `share-targets` | 只读扫描，非 macOS 返回空 |
| `open-with` | 应用路径必须 **`realpath` 之后**落在 `/Applications` 或 `/System/Applications` 内、且以 `.app` 结尾 |

⚠️ **`open-with` 的路径判据必须解析后再比**。第一版写的是 `startsWith("/Applications/")`，
而探针量出：`/Applications/../tmp/Evil.app` **通过了前缀判据** —— 只要那个文件恰好存在，
它就会被放行，而真实的应用根本在别处。改成 `fs.realpathSync` 之后逐条复量：
`/Applications/WeChat.app` 允许、`/System/Applications/Mail.app` 允许、
`/tmp/Evil.app` 拒绝、`/Applications/../tmp/Evil.app` 拒绝、`/Applications/WeChat.app/x` 拒绝。

## 四、验证

界面冒烟（fixture 那一节，工作目录里有真 png + 真 wav，且**那次运行里群不会有新消息**）。
**418 ok / 0 FAIL**（本轮起点是同一天早些时候那次全绿；新增 17 条断言）：

- **自动展开**：收起面板 → 往工作目录写一个新文件 → 面板**自己**回来，而且新文件已经在列表里
  （实测 `["zz-autoopen.txt","narration.wav","shot.png"]`）。
  ⚠️ 这一节比别的都严：fixture 的群没有新消息，所以面板自己那条「按时间戳刷新」的路不会响，
  它能回来就只可能是新加的轮询做到的。
- **反过来**：收起后等 9 秒（跨两个轮询周期）不许自己弹回来。
- **右键菜单**：弹出、完整落在窗口内（实测 `[1419,129,1627,416]`，窗口 1680×963）、
  **没有被列表或预览压住**（`elementFromPoint` 量菜单中心那一点，z-index 60）、顶上写着对这一条、
  五个动作都在、两个分享目标都在（`share:wechat` / `share:mail`）。
- **参数对不对**：点「用它的默认程序打开」→ 交给外壳的是 `…/workspaces/<gid>/zz-autoopen.txt`
  （**绝对**路径）；点「用微信打开」→ `("/Applications/WeChat.app", 那个路径)` 两个参数；
  点「复制这个文件」→ 同一个绝对路径。
- **能力缺席时**：把外壳能力撤掉（真的浏览器里就是这样）→ 菜单**只剩** `["view"]`。
- 动作做完**有一条回话**（`.toast` 非空）；Esc 能关掉菜单；点完一项菜单自己收起。

⚠️ 为了让断言按**结构**而不是按文案，菜单项带 `data-act="view|open|reveal|copy|copy-path|share:<id>"`。
⚠️ 分享目标在 fixture 里是**桩**(两个固定应用):「这台机器真装了哪些」由主进程扫描,那一层用探针单独量过
（见第三节末尾的逐条结果）。

⚠️ 写这段测试时踩到的坑（记下来免得再踩）：**派 `contextmenu` 事件和读菜单必须分成两次往返**。
第一版把两件事写在同一个同步块里，于是永远读到「没弹出」—— React 的状态更新是异步批处理的，
同步块里 `querySelector` 拿到的是上一次渲染的 DOM。另外 `menu.acts` 在没弹出时是 `undefined`，
`undefined.every(...)` 会把整个脚本打断（后面所有断言都不再执行）。

## 五、顺手修掉一处「违背组件自身注释」的浪费

`OutputsPanel` 的注释写着「不靠轮询,靠 `stamp` 一变就重取」,但 `load` 的依赖写的是 **`group` 对象**。
`useData` 每隔几秒就换一批新的群对象 → `load` 每次都变 → 那个 effect 每次都重跑 →
**面板一开着就在反复重取整个工作目录**(工作目录大时每次都是一次真实的全目录 rglob)。
实测:一次应用会话里 `GET .../workspace` 被打了一千四百多次。

改成依赖 **`group?.id`**:面板只在「换群 / 有新消息 / 点了刷新」时重取 —— 那正是注释里说的那三件事。

## 六、验证时踩到的两个坑(都记在测试的注释里)

1. **`/tmp` 是符号链接,比较路径要先规范化。** 断言原本拿 `fixture.dir`(`/tmp/ta-ui-fixture`)拼出期望值,
   而后端给的是**解析过**的路径(`/private/tmp/...`) —— 同一个文件,两个拼写,字符串不相等。
   **功能是对的,红的是断言。** 这个项目为同一件事踩过一次(`coderun` 的路径守卫),这是第二次;
   所以比较改成两侧都 `fs.realpathSync`。
2. **派事件和读 DOM 必须分成两次往返**(React 异步批处理),以及**未弹出时 `menu.acts` 是 `undefined`,
   `undefined.every(...)` 会把整个脚本打断** —— 第一版就是这么让后面所有断言都不再执行的。

## 七、顺带查出并修掉两条**偶发**变红的断言（同一类：固定等待 / 元素没钉住）

跑最终验证时冒出来两条与本次改动无关的失败，各自紧接着的那条断言**都是过的** ——
说明功能没问题，是断言读得不对：

| 断言 | 真相 | 改法 |
|---|---|---|
| 「筛选后只剩匹配的那些 (6160 < 6160)」 | 库长到 **6160 篇**之后，一次筛选查询有时超过它固定等的 **1.5 秒**；而紧随其后的「列表里确实是匹配的文档」是过的。 | **等答案**而不是等一段固定时间：轮询到数字真的下来（≤10 秒） |
| 「点赞后那个键是亮着的 (0 个亮)」 | 那一段每一步都重新 `.pop()`（取最后一条成员消息）—— 等于假设点击与读取之间列表没变，而应用一直在轮询并重渲染。**后端确实记下了这条好评**（下一条断言过的）。 | 先把目标**钉住**（`.msg[data-mid="…"]`），7 处 `.pop()` 全换成按 id 选；并加一条自检「钉住了要操作的那一条发言」 |

两条都重复跑一次没有复现 → 确认是**偶发**，不是常驻。但它们和上一轮清掉的那 8 条是同一个病：
**断言要等「要验的那件事成立」，或者把目标钉死** —— 而「跑一次是绿的」并不能说明它下次也绿。

⚠️ 同一轮里还踩到第三次「读得太早」：新文件那一节一看到面板在就断言「新文件在列表里」，
而面板先挂上去、工作目录那一趟请求随后才回来 → 读到空数组。改成**等到两件事都成立**为止。
（这一条和第 1 条、第 2 条是同一个教训：这个项目里「点 → 等一拍 → 再读」的纪律，还要加上
「等到条件成立」这一档。）
