# 「视频专区」设计：场景 / 表情动作 / 音乐生成（2026-09-27）

用户的需求原话：**「视频专区包括视频场景、表情动作、音乐生成等，用户可以在里面定义生成，并选择。
同时音乐生成类似 seedmusic，可以根据提示词生成背景音乐，并可以试听。」**

这份文件先讲**现在各到什么程度**（避免重造），再讲**专区怎么组织**，最后是**分期**与**待确认**。

## 二、专区怎么组织

一个页面，三块，每块都是同一个三段式：**定义 → 生成/预览 → 选择**。

```
视频专区
├── ① 音乐          [现在就能做]
│     · 输入：风格标签（genre / instruments / mood / bpm）、时长、seed
│     · 生成：后台任务 + 进度（ACE-Step 要几分钟，不是几秒）
│     · 试听：内嵌播放器（这一条是用户明确要的）
│     · 上架 → 进曲库 → 曲库里试听/删除/选用
│
├── ② 视频场景      [定义待确认]
│     · 定义：名称 + 用途 + 描述 + 参考图 + 画幅/配色/光线
│     · 生成：一张预览，确认"这就是我要的场景"
│     · 选择：给某个项目或某个镜头指定
│
└── ③ 表情动作      [定义待确认]
      · 定义：名称 + 类别（机制动效 / 角色表情 / 运镜）+ 可调参数
      · 生成：预览片段
      · 选择：给镜头指定
```

**⚠️ 三块都别另起一套存储**。项目里已经有「用户可加的模块」的成熟先例
（`workflows` / `layouts` / `voices` / `music` 四个注册表：热加载、解析失败点名、
重名报错不覆盖、未知名字列出已有的而不回落）。场景与动作应照这个模式加 `scenes` / `motions`，
而不是发明第五种做法。

## 三、分期

| 期 | 内容 | 为什么这个顺序 |
|---|---|---|
| **第一步（可立即开工）** | **音乐**：后端 4 个接口（列表 / 试听 / 生成 / 删除）+ 前端页面（提示词 → 生成 → 试听 → 上架） | 生成链路**已经跑通**，缺的只是壳；而且"能试听"正是用户点名的需求 |
| 第二步 | **场景**：确认含义后加 `scenes` 注册表 + 定义/选择界面 | 需要先定清楚它和 `layouts`（版式）的关系 |
| 第三步 | **表情动作**：确认含义后加 `motions` 注册表 + 给镜头指定的界面 | 同上；且"角色表情"要接数字人链路，成本更高 |

## 四、待确认（挡在第二步/第三步前面）

**①「视频场景」指哪一种？**（决定是复用 `layouts` 还是新建 `scenes`）

- (a) **片子的版式与风格** —— 标题卡、落款、字幕位置、配色、节奏 → **这个已经有 `layouts.py`**，只是没界面；
- (b) **画面里的环境场景** —— 手术室 / 血管内视角 / 诊室 / 户外 → 这是**给生成图或视频用的场景**，现在完全没有；
- (c) **预制镜头模板** —— 开场 / 讲解 / 演示 / 收尾这种结构化的镜头段落。

**②「表情动作」指哪一种？**

- (a) **机制/示意动效** —— 血流、瘤囊鼓出、弹簧圈填塞 → **已有 5 个固定预设**，但用户不能自己定义；
- (b) **数字人的表情与动作** —— 眉眼、口型、手势 → 走 ComfyUI + InfiniteTalk / LivePortrait，成本高；
- (c) **镜头运镜** —— 推 / 拉 / 摇 / 移 → `assemble` 里有 `camera`，没界面。

**③ 音乐那一块的两个小决定**：试听用内嵌播放器就够了，还是要能"边听边挑、挑完直接给某个项目配上"？
以及要不要保留 `seed`（同一个提示词用同一个 seed 才可复现——建议保留，但要放在高级选项里）。

## 五、作曲面板的重做：从「五台推子」到「一句话」（2026-09-27 下午）

用户原话：

> 生成音乐这块布局看起来有点乱，用户填提示词后自动选择音乐生成方式，及歌词可选填，然后再生成音乐。
> 这种算法可以参考 seedmusic 的算法。页面设计也可以参考 seedmusic 页面设计。可以保留人声选择。
> 情绪也没必要放到面板上，这些都在算法里面，算法根据提示词进行选择对应的音乐生成方式，不用在面板中展示出来。

### 之前错在哪

上一版把 ACE-Step 的五条硬规矩（流派第一、具体乐器、BPM 对区间、不超词数、不矛盾）做成了**五台推子**：
6 个场景预设 + 12 个流派 + 16 件乐器 + 10 种制作 + 情绪下拉 + 速度滑杆 + 一句补充描述。规矩是对的，
**对象错了**：一个做视频的人想的是「来一段安静的、别抢话的底」，不是「我该选哪种制作手法」。
那一屏要读、要点、要理解，最后还未必对。

### 现在是什么

面板上只剩**三样**：

| 控件 | 为什么留 |
|---|---|
| **描述**（必填，最大的地方） | 用户真正会写的东西：用在哪、什么乐器、什么感觉 |
| **歌词**（可选） | 留空 = 纯器乐 |
| **人声**（默认「自动」） | ⚠️ 唯一留着的手动项：唱不唱、谁来唱，是作者真会有意见的一件事 |
| 时长 / 标题 | 一行上的两个小格，片子配乐确实需要一个长度 |
| 高级：语言 / 种子 | 收在折叠里 |

然后：「**读成**：极简钢琴 · 平静 · 三角钢琴 + 温暖铺底 · 65 BPM」——一行回执，紧跟在描述下面。
算法决定的那些**不再出现在面板上**，但**必须说得出来它读成了什么**；否则「自动」就是个黑箱。
模型真正收到的那串标签收在 `详情` 里（默认不展开）：用户要的是不看见，不是查不到。

### 算法：`musicprompt.read()`

一句人话 → 五个参数。**确定的**（一张中英双语线索表 + 每个流派自带的一套标准配器），不是模型调用：

* 不花 token、离线可用；
* **可以写断言** —— 「一句安静钢琴不该读出鼓」「读出来的词自己必须干净」这种话，只有确定的实现才验得了；
* 将来要用模型读更自由的表述，**换的是这一个函数**，不是调用它的地方。

几条会踩到的规矩，都写进了实现：

* **否定要算数**：「不要鼓」里也有「鼓」字，不特判就会反着读（`test_asking_for_no_drums_really_drops_the_drums`）；
* **同家族的乐器不并列**：第一版实测出过 `grand piano, felt piano` 两个钢琴 —— 那不是更丰富，是两条
  几乎一样的线索互相稀释；
* **速度词在区间内挪**，不写死数字：「慢的浩室」如果变成 70 BPM，正是会让模型来回摇摆的那种输入；
* **读不出来就说读不出来**：用默认底子（`documentary`，因为它的用途是「真实病例、访谈、资料画面」），
  并把这件事写进回执；
* **情绪跟着流派走**：预告片配乐配「中性」是两回事（trailer → epic、dark-ambient → tense…）；
* **歌词与「纯音乐」冲突时按歌词走**，并且说出来。

⚠️ 一处机械守卫：`_MOOD_CUES` 的键必须与 `music.MOODS`（曲库的闭词表）**一模一样** —— 多一个词会让
上架被拒，少一个词会让某个情绪永远读不出来，而两处各自看着都很对。

### 参考了 SeedMusic 什么

**页面形态**：一个大输入框 + 一个可选歌词框 + 一个「要不要人声」+ 一个生成按钮，其余全在算法里。
**算法形态**：描述 → 结构化条件 → 生成。区别在于 Seed-Music 用模型来理解描述，这里用一张线索表真值表；
理由如上（可验、离线、零成本），而且以「一句话描述 + 封闭词表」这个任务规模，线索表已经够用。

### 顺带：面板撤了推子之后，`/music/vocabulary` 里没有读者的字段清掉了

`moods` 唯一的消费者就是那个情绪下拉 —— 一起删（`music.MOODS` 仍是唯一那份，由上面那条断言守着）。
`presets`（6 个场景预设）**没有删**：专区页的「模板」那一块读它，那是它们的正经去处。

### 下一步（未做，一行的事）

群成员用的工具 `make_music` 现在仍然直接收**标签串**（它的说明就是这么写的）。把 `read()` 也接到
那条路上，就是 `toolhub._make_music` 里把 `prompt` 先过一遍 `musicprompt.read()` —— 那样
「一句话怎么变成标签」就只有一处，而成员随手写一句中文也不会再产出通用钢琴。
没做的原因：它改的是成员侧的行为（已经开着的群在用的东西），值得单独跑一轮、单独说清楚。
