# 侧栏的「专区」——它是什么、现在有什么、还缺什么（2026-09-27）

用户原话：

> 把右侧栏里面的技能、插件、钩子、MCP、智能体与本地工具、聊天通道都放到用户面板里面，
> 这个地方留着给后续的专区用，包括视频专区、写作专区、故事专区、创作专区等。每个专区有
> 专门的资料库、模版，工作流、不同分工可选择的工具或者 skills 等。

这一轮做了三件事：把六个配置入口搬进用户面板；把侧栏那一格改成**专区**；给每个专区立出
用户点名的**四块**（资料库 / 模板 / 工作流 / 分工与技能），并让视频专区真的接上。

---

## 0. 最终落法（同一天的第二轮：用户改了口）

第一版把六个入口搬进了**用户面板**（左下角那个弹层）。用户随后纠正：

> 技能、插件、钩子、MCP、智能体与本地工具、聊天通道都**移到用户设置面板提示词、资料库那个
> 工具栏里**。

所以它们的家在**设置面板的导航**里 —— 与提示词（Prompts）、资料库（Library）、记忆（Memory）、
模板中心同一根工具栏，自成一组 **Capabilities**。用户面板恢复原样。

这条改动的连锁反应（一处都不能漏）：
- `App.goTab` 对这六个 id 不再「关掉设置、跳到主区域」—— 它们现在是设置里的一页；
- `CapabilityWorkspace`（「这些能力接到哪个群」那条栏）**跟着搬进设置内容区**，
  否则页面上「接入本群 / 从本群移出」的按钮就没有群可指（它们读的是那个 context）；
- 主区域那条渲染分支与 `AREA_PAGES` 随之删除（`appearance` 是唯一还留在主区域的）；
- 用户面板里那一段（含 `.menu-cap` 分组小标题）整段撤掉 —— 两处入口等于改一处就有一处是旧的。

## 1. 为什么这么分：两种东西不该挤在一格里

侧栏那一格原来叫「能力中心」，装着六个入口：技能、插件、钩子、MCP、智能体与本地工具、
聊天通道。它们有共同点，也有决定性的一点不同：

| | 配置类（六个入口） | 专区 |
|---|---|---|
| 何时用 | 配一次，之后偶尔回来瞄一眼 | 每次打开程序就是来这儿的 |
| 里面是什么 | 开关、名单、通道、密钥 | 你做出来的东西，以及做它用的模板与流水线 |
| 放哪儿合适 | 设置面板的工具栏（和提示词、资料库同一类） | 侧栏（和项目列表同一类） |

所以六个入口搬进设置，是一句「归位」而不是「藏起来」：它们和提示词、资料库并列，点开仍是
整页 —— 只是不再占着主区域，也不再占着用户面板。

侧栏那一格改成**专区**之后，它的含义单一了：**这里是做东西的地方。**

## 2. 一个专区：声明四块，页面上画三块

`backend/app/zones.py` 是唯一出处。一个专区声明四样东西 —— 那是用户点名的那四样：

| 块 | 内容 | 视频专区里是什么 |
|---|---|---|
| **资料库 library** | 这个专区自己攒下的东西 | 音乐库（实时计数）、我的素材（实时计数） |
| **模板 templates** | 起手件：挑一个，不从空白开始 | 作曲台的六个场景预设（**从 `musicprompt` 读，不重打一遍**） |
| **工作流 workflows** | 能跑的流水线，以及**能不能跑** | 机制动画 / ACE-Step / 静图转动作 / 口型 / 场景静帧 / HTML 渲染链 |
| ~~**分工与技能 roles**~~ | ~~谁坐哪个位子，那个位子拿到哪些工具与 skills~~ | **声明但不在页面上画** |

⚠️ **画的是三块，不是四块。** 用户 2026-09-27：**「在视频专区里面的各个面板里不需要放分工、
工具与技能。」** 所以 `zones.DRAWN = (library, templates, workflows)`，`detail()` **也不再把它
塞进响应** —— 送过去却没有页面会渲染的东西，正是这个项目反复在治的「等于不存在」。

`roles` 没有消失，它只是不在这一页上：数据仍在注册表里、仍被四条守卫验着（技能名 / 工具名 /
群模板 id / 成员名都存在，且 `in_template` 与群模板的成员表一致）。它将来是**从这个专区起一个
群**时那份名单 —— 那时它是一条动作，而不是这一页上的一节。

三块用**同一套渲染**（`pages/ZonePage.tsx`）：它们在四个专区里形状完全一样，差别只在内容。
三份布局意味着每加一个专区就要再挑一次「这一块该长什么样」，而用户看到的是四个专区四个样子。

⚠️⚠️ **三块是只读的索引，不是一堆按钮。** 能做事的入口只有一处 —— **工作台**
（视频专区就是上面那四个标签页）。在索引里塞一个「点了没反应」的按钮，正是这个项目这一周
反复在处理的那类问题。所以每一项只有三样东西：名字、状态、一句说明。

## 3. 状态词是承诺，所以它有几个，且各有各的意思

```
ready     现在就能用
partial   能用，但有代价（例如静图转动作：无声、几十分钟一条）
blocked   建了，但本机有东西挡着 —— 必须说清挡的是什么
planned   还没建 —— 页面如实说它将来长什么样
```

`blocked` 与 `planned` **故意分开**：它们的下一步不一样，用一个词概括会把用户送去错的那一步。
后端有一条断言守着「blocked 必须说清卡在哪」（`test_a_blocked_workflow_says_what_is_blocking_it`），
还有一条守着「标着 ready 的专区里至少有一件能跑的事」（`test_a_ready_zone_has_something_that_actually_runs`）。

## 4. 现在四个专区分别是什么状态

| 专区 | 状态 | 说明 |
|---|---|---|
| **视频专区** | `ready` | 工作台能用（作曲、我的素材），四块里资料库有实时计数、模板来自作曲台 |
| **写作专区** | `planned` | 四块已声明。今天能用的部分：`write_document` 出稿、四个现成群模板（研究报告 / 方案撰写 / 办公文档 / 翻译校对）。缺：一篇东西自己的草稿架、把多份文档收成一篇的流水线 |
| **故事专区** | `planned` | 创作写作群模板今天就有。缺：人物与节拍这两个架子、以及「不让故事自相矛盾」的机械核对 |
| **创作专区** | `planned` | 参考图库（513 张器械照 / 43 类）**已经在盘上并同步进群**；绘图专家也在。缺：生成图（云端没额度、本机没图像模型） |

## 5. 「不同分工可选择的工具或者 skills」现在放在哪

**数据在，页面不画。** 每个位子声明：**成员名**（必须是内置成员）+ **工具** + **skills** + 一句职责，
由五条断言守着（见 §2）。它解决了「一个位子的工具来自 `toolhub`、skills 来自技能目录、名单来自
群模板」这件事散在四处的问题 —— 但**不是画在专区页上**。

下一步（**未做**）：把这份分工用在「从这个专区起一个群」上 —— 入口是
`templates.create_group_from_template()` 的 `ext.skills` 与 name 参数。到那时它是一条动作。

## 6. 以后再加一个专区，改哪里

- **只要没有新的生成引擎** → 丢一个 JSON 进 `<数据目录>/zones/<id>.json`，字段与 `BUILTIN`
  里那份一致（`name`/`blurb`/`icon`/`state` + 四块）。三条规则沿用 `layouts.py` 的：
  读不了的文件**点名带原因**、坏值**报错而不是取默认**、与自带专区**重名的文件被拒绝**
  （静默覆盖一个自带专区，等于改了一个用户没碰过的页面）。
- **要新的生成引擎**（像视频专区那样）→ 那是代码，不是文件。JSON 只能描述可以描述的东西，
  这一点是事实，不是这里定的规矩。
- `icon` 只能是 `zones.py` 里 `ICONS` 那几个名字，写错了会被拒绝并列出有哪些 —— 否则它
  会渲染成一个默认图标，而没人会发现。

侧栏与专区页都从 `/api/zones` 读，**前端不留第二份清单**：加一个专区只改一处，而漏掉的那一处
原本只会表现为「侧栏里没有它」。
